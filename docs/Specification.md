# Tellurian Trains Drawing – Specification

Status: **Draft 0.28** (2026-11-19) – for review. Implementation plan: [ImplementationPlan.md](ImplementationPlan.md).
Requirement IDs (e.g. `MD-12`) are stable and are referenced from the implementation plan.
Priority: **M** = must (first release), **S** = should (first release if time allows), **L** = later.

---

## 1. Purpose

A progressive web app (PWA) that anyone can use to:

1. **Draw end profiles**: the cross-section of a module end, with its end plate, track positions, screw holes and ground line.
2. **Draw modules**: the baseboard outline, the track plan and the module ends (exits) with their end profiles.
3. **Plan a layout in a hall**: put modules in order, so the app joins them end to end, place the result in a drawing of the hall, and check that the layout fits physically and technically.

**All drawings are 2D.** End profiles are drawn in *end view*. Modules, halls and hall plans are drawn in *plan view* (from above).

The app is a client-only **AOT-compiled Blazor WebAssembly standalone app**. It runs offline and stores data in the browser. Users share their work by exporting and importing files.

## 2. Scope

### In scope (first release)
- End profile drawing editor, with fit comparison between profiles.
- Module drawing editor (outline + track plan + exits).
- Local catalogue of scales, module standards and end profiles, bundled with the app and editable by the user.
- Hall editor (walls, pillars, doors, no-go zones).
- Hall planning: collecting module files (ZIP, shared folder), ordering modules into lines, flipping, branching, validating joints, clearance checks, loop closure checks, statistics.
- Local storage, file import/export, printing and export.

### Out of scope (first release)
- Integration with the Module Registry. A read-only import is planned for a later phase (§10).
- User accounts, rights/roles, servers, cloud sync and real-time collaboration.
- Submitting modules to meetings and managing meeting registrations (done in the Module Registry or as the meeting organiser decides).
- 3D of any kind, scenery details (buildings, roads, water), electrical/DCC wiring.
- Running operations or timetables on the layout.

| **Anchor dimensions** | The measurements that tell the people setting up where to put the anchor module in the hall. | A **reference point** on the anchor module (an end-plate corner, an exit centre or a marked point); two **reference elements** in the hall (walls, a wall and a pillar, or two pillars); the distances from the reference point to them; the angle to a reference wall. |
| **Line entry** | One module in a line. | Module, **turned** or not. Not turned: the module's left exit joins the previous module and its right exit the next. Turned 180°: the other way round (a **flip**, HP-4). Only for a module with three or more exits: the exit the line **continues from**. |
| **Public area** | An area of the plan where visitors have access. | Polygon, label/note. |
| **Walking path** | A path for train drivers to walk along while following their trains. It may pass under duck-under parts of modules, but not through other modules. | Centre line (open path of line/arc segments), width (default 600 mm, configurable per plan), label. |
| **Placement** | One module placed in a hall plan, i.e. a line entry seen together with its computed pose. | **Joint** | Two placed exits connected to each other. | **Acknowledgement** | A planner's decision that a specific warning in a hall plan is OK. This is typical for single-track modules of different standards, e.g. FREMO H0-RE and MMM-2R. Shown with a clamp symbol at the junction. | Number of clamps (default 2), note. |

### 3.1 Geometry conventions
- Units are **millimetres** and **degrees**, and all values are stored at full model size (no scaling to the real world).
- **Plan view (modules, halls, hall plans).**
  - Each module drawing has a **local coordinate system**. The drawing lies the way the module is seen: the viewer stands below it, on the viewing side, X points to the viewer's right and Y away from the viewer, and the origin is at the first Left exit. The user decides how the module lies (a chosen track horizontal, turned 180°, or a curve laid symmetrically); turning rotates the stored geometry, and the exits' directions follow from it (ModuleDrawing.md §2). All sections of the module are drawn in this system, assembled as they are when the module is set up.
  - An **end plate** is a straight stretch of a module's outline where it meets other modules; it carries one or more exits. An **exit pose** is a point (the centre of the exit's end profile on the plate's joint face) plus a heading that points **out of** the module; it follows from the plate and the exit's offset along it (ModuleDrawing.md §4.2).
  - Two exits are **joined** when their positions coincide and their headings are opposite (180°).
  - A hall plan refers to an exit by its **side and number** on that side, e.g. *Left 1*, *Right 2*, *Up 1*: numbered by position in the drawing: Left and Right exits from top to bottom, Up and Down exits from left to right (ModuleDrawing.md §4.4). It never refers to an exit by its label.
  - Modules are rigid bodies. A placement may be **translated and rotated, never mirrored**, because a physical module can't be mirrored.
  - **Height** is not part of the 2D geometry but carried as data, always as an **offset from the standard's rail-top height** (0 = standard, normally 1300 mm above floor). Each exit has a rail-top offset (ramp modules) and each placement a leg adjustment. The **effective rail-top offset** of an exit in a hall plan = exit offset + placement leg adjustment + (standard's rail-top height − hall plan primary standard's rail-top height).
- **End view (end profiles).**
  - The end face is drawn **as seen from outside the module, looking at it**.
  - X is lateral (positive to the right), Y is vertical (positive up).
  - The origin is on the end-plate centre line, and **Y = 0 is the top of rail** (Swedish *RÖK*, *rälsens överkant*). Everything else (plate edges, screw holes, ground line) is measured from it, so profiles with different plate heights are compared correctly.
  - The height of rail top above the floor comes from the standard (default 1300 mm). It is used to show floor-related heights, but it plays no part in comparing profiles.
  - This view links to the plan view through the exit pose: the end view's X axis is the exit's lateral axis.
- **Facing ends.** When two module ends are joined, each end is seen from outside its own module, so A's right side meets B's left side. To compare two profiles, A's drawing is **mirrored about its centre line** (X → −X) and laid over B's drawing.

### 3.2 Joint fit rules
Each joint is classified by laying the **mirrored drawing of end A over the drawing of end B**, taking the exit orientations into account (§3.1). The rules are evaluated top-down and the first one that matches decides the result. A catalogue override (§3) for the pair, if present, replaces the result.

| # | Condition | Result | Colour | Join method |
|---|---|---|---|---|
| 1 | **Track geometry differs**: number of tracks, track positions (i.e. c/c between double tracks), gauge or 2R/3R don't match within the joint tolerance. | **Incompatible** | Red | – |
| 2 | Tracks match, but the **screw holes don't line up** (e.g. single-track modules of different standards). | **Fits with clamps** | Yellow + clamp symbol | Clamped |
| 3 | Tracks and screw holes match, but the **ground line doesn't match**, e.g. asymmetric profiles turned the wrong way. | **Fits with mismatch** | Yellow | Bolted |
| 4 | Tracks, screw holes and ground line match. | **Fits** | Green | Bolted |

Notes:
- **Screw holes decide how ends are joined.** If the screw holes don't match, the ends are either incompatible (the tracks don't line up, rule 1) or joined with clamps (rule 2).
- **Plate size is not a fit criterion.** Plates of different height (or width) are compared only through their screw holes, tracks and ground line. The plate outline is drawn and shown in the compare view for information only.
- **Tolerances.** Track positions and screw holes use the joint tolerance (default 0.5 mm). The ground line uses a looser landscape tolerance (default 2 mm). Both are configurable.
- **Screw holes match** when every hole in the mirrored set A lies on a hole in set B, and vice versa, **or when at least three holes line up**: three bolts hold the ends together with enough stability, e.g. a low and a high profile of the same family (FREMO H0-B96). The minimum is configurable. Positions are relative to rail top and the centre line. If either profile has no drawn holes, the screw-hole pattern identifiers are compared instead. If neither is available, the result is reported as "screw holes unknown" (warning) and the joint is assumed to be bolted.
- **Symmetry is derived automatically.** A profile is symmetric when its drawing equals its own mirror image within tolerance. The orientation setting on an exit only matters for asymmetric profiles.
- **Colour is never the only signal.** Each fit has its own symbol as well (✓, !, clamp, ✕), for colour-blind users and black-and-white prints.

## 4. Users and main use cases

The use cases are described in detail in [UseCases.md](UseCases.md).

**Anyone can use the app** to draw end profiles, modules, halls and hall plans. The app has **no accounts, rights or roles**: every user can do everything with the data on their own device.
Roles and access rights exist only **outside** the app. For example, the Module Registry defines which module data a user may see or change, and a meeting organiser decides how modules are submitted to a meeting.

Typical scenarios (not roles):

| Scenario | Description |
|---|---|
| Draw an end profile | One of a few selected persons (e.g. appointed by FREMO or MMM) draws an end profile from a standard's specification sheet, and publishes it with the end profile in the Module Registry (§10). Everyone else imports it and uses it in module drawings. |
| Check end profile fit | Someone compares two end profiles to see whether and how they fit, e.g. before joining modules of different standards. |
| Draw a module | The module owner, or someone drawing on the owner's behalf from data the owner provides, draws a module and saves it as a module file. The owner or the drawer uploads it to the Registry or another shared location. They can share it in any way they like, and in a coming release they can upload it to the Module Registry (§10). |
| Draw a hall | Someone draws a hall and shares the hall file. |
| Plan a layout in a hall | Someone collects module files and builds and validates a hall plan in a hall. They then print it or share the hall plan file. Typically this person is a meeting organiser. |
| View a hall plan | Someone opens a shared hall plan file, for example to see where their modules go. |
| Maintain catalogue data | Someone edits standards, end profiles and overrides and shares a catalogue file. |

**Submitting modules to a meeting is not part of the app.** It is done through the Module Registry or in whatever other way the meeting organiser decides, such as e-mailing module files. The app only reads and writes the files.

## 5. Functional requirements

All three editors (end profile, module, hall) share the same drawing canvas: pan/zoom, grid, snapping, selection, measurement, undo/redo and autosave (MD-11, MD-12, AP-3, AP-4 apply to all of them).

### 5.1 Catalogue (CA)
| ID | Pri | Requirement |
|---|---|---|
| CA-1 | M | **The app has no catalogue of its own (decided 2026-11-22; until then it shipped a built-in one).** A new user's catalogue is empty, and the app says how to fill it: by importing a catalogue file (CA-3), e.g. one published by a club or a standardisation body, later by importing from the Module Registry (CA-5), or by adding entries by hand (CA-2). A catalogue (JSON, versioned) holds scales, module standards, **end profile drawings**, add-ons and compatibility overrides; each end profile references its source document and revision, e.g. the FREMO or MMM (MälarModulMöte) PDF drawing it is drawn from. Scales are chosen from the suite's list of scales also when the catalogue is empty. |

An end profile can be copied and then edited. When a module is opened, the end profiles it embeds that the catalogue lacks are listed, and the user can save them in the catalogue (decided 2026-11-22). |
| CA-3 | M | The catalogue can be exported and imported as a file. Importing a catalogue file brings its scales, standards, add-ons and overrides, and the end profiles the user chooses; an entry with the id of one in the catalogue replaces it, one with a new id is added. **Standards are merged by id or short name: a catalogue never has two standards with the same name.** An imported standard replaces the one with the same id or name; its values take precedence and the replaced standard fills in only what it lacks (the countries are always the imported ones). End profiles and add-ons of the replaced standard move to it, and a module whose standard id is gone finds its standard by name (decided 2026-11-26). |
| CA-4 | – | *Replaced by EP-1…EP-9.* |
| CA-5 | M | The catalogue can be fetched from the Module Registry (§10) with *Fetch from the Module Registry* on the Catalogue page: its public catalogue (`GET https://moduleregistry.azurewebsites.net/api/catalogue`, no API key), limited to the user's scale (AP-9) and country (CA-6) when they are set. It is merged as a catalogue file is (CA-3). The Registry's end profiles that it has no drawing of come **without a shape** (no outline, only designation, scale, standards and the Registry's id). Such a profile is kept in the catalogue and marked *no drawing*; *Create drawing* opens the new end profile form for it, and the drawing keeps its id, designation, scale, standards and external references, so saving it in the catalogue replaces the profile without a shape. A profile without an outline can't be chosen for a module exit, since its plate has no width. Importing one never replaces a drawn profile in the catalogue: the drawing is kept, and it takes the imported designation, scale, standards and external references. **Merge:** when a drawn profile has another id but the same designation, scale and standard (by id or short name; a profile without standards matches any) as an imported one without a shape, they become one end profile: the drawing gets the imported (the Registry's) id, its standards are added, and the catalogue's overrides and standard defaults move to the new id. The former id is remembered in the browser, and a module that uses it is moved to the merged profile when it is opened (decided 2026-11-26). |
| CA-6 | M | **Country-specific standards**: a module standard can name the countries it applies to (ISO 3166 two-letter codes); without countries it applies everywhere. For example, MMM-2R and MMM-3R apply in Sweden only and the FREMO standards everywhere. Standards for other countries than the one in the settings (AP-8), with their add-ons, the end profiles that belong only to them and overrides of those end profiles, are **not offered as choices** (catalogue lists, new module, new end profile, editors). With no country chosen, only standards that apply everywhere are offered. Drawings that use such a standard still open and show as usual. |

### 5.3 Module drawing (MD)
The structure of a module drawing (exits → end plates → sides → sections → tracks → zones), the auto-draw rules and the visual style are defined in detail in [ModuleDrawing.md](ModuleDrawing.md).

| ID | Pri | Requirement |
|---|---|---|
| MD-1 | M | Create, open, duplicate, rename and delete module drawings. Show them in a searchable library (by name, owner, standard, flags). |

## 6. Data storage and file formats

- **Files are primary.** The JSON file is the result of every drawing. Users keep, share and upload files.
- **IndexedDB is the workbench** for work in progress: autosaved **drafts** (one per open drawing, with an "unsaved changes" flag), **recent files** (with file handles where the File System Access API allows re-opening), the **module collections** of hall plans, the user part of the catalogue, and settings. Each stored drawing is one JSON document with `id` (GUID), `schemaVersion`, `revision` (incremented per save) and `modified` (UTC). The app reminds the user to save a file when a draft has unsaved changes.
- **File format**: UTF-8 JSON with an envelope `{ "format": "tellurian-drawing", "kind": "EndProfile|Module|Hall|HallPlan|Catalogue", "schemaVersion": n, "appVersion": "...", "content": {...} }`.
  File names: drawing files are **plain JSON files** (`.json`), so they open in any JSON editor and upload to the Module Registry as JSON. The app suggests names with the kind before `.json`: `.endprofile.json`, `.module.json`, `.hall.json`, `.hallplan.json`, `.catalogue.json`. The kind is always read from the content (`format`, `kind`), so a file with any `.json` name opens; JSON files that aren't drawing files are skipped when importing. Files with the extensions used up to version 0.4 (`.tdendprofile`, `.tdmodule`, `.tdhall`, `.tdhallplan`, `.tdcatalogue`) still open (decided 2026-11-15).
- **Self-contained files**:
  - a **module file** contains the module with its one drawing and embeds the end profile drawings its exits and internal joints use, so the receiver (another user or the Module Registry) can show and check the ends;
  - a **hall plan file** embeds copies of the hall, every module drawing it uses and their end profiles, so anyone can open it.
- **Identity**: drawings keep their GUID when exported and imported, so the same physical module or the same end profile is recognised again. What other systems know a drawing as is kept apart, in the external references below.
- **External references**: every drawing (module, end profile, standard, hall, hall plan, catalogue) can have an `externalReferences` section with **one entry per system**, e.g. `moduleRegistry`. Each system owns its entry and alone decides what is in it; the app reads an entry as JSON and **writes it back unchanged**. The Module Registry's entry holds its ids: the id of a module, an end profile or a standard. Embedded copies (the end profiles in a module file, the modules in a hall plan) carry their sections with them. **A copy loses the section**: a new drawing made from an existing one gets a new GUID and no external references, or it would point to what the original is registered as.
- **Names in a file**: property names are camelCase; enum values are written as in the code, e.g. `Left`, `SignalControlled`, as in the shared layout model (§10). Enum values in camelCase, as files were written before schema version 2, are still read.
- **Owners** of a module are saved as **one text with their names**, separated by commas (`moduleOwners`), and the module has its `prefix`; nothing else: no shares, contact details or ids.
- **Unknown properties are kept**: a property that this version of the app doesn't know, on any object in a file, is written back at a save. A file from a newer version within the same schema version, or with an addition from another system, is then not damaged.
- **Migration**: older schema versions are upgraded on load. Newer versions are refused with a clear message. Changes that aren't additions are collected in one new schema version per file kind (version 2, not yet released: external references, owners, left and right, one drawing per module, operation location, hall plan lines of modules that are turned or not, exits by side and number, the module of the shared layout model, enum values as in the code; `schemas/CHANGELOG.md`). All five file kinds are at version 2.
- **Published schema**: JSON Schemas for all file kinds, with examples, are kept in the repository in `schemas/` (not deployed with the app). They are generated from the code and checked by tests. The **module** and **end profile** schemas are consumed by the Module Registry (EX-7), so changes to them must be coordinated with the Registry.
- **Self-describing references**: a module file includes its catalogue references by value (standard short name, scale, end profile designations) as well as by id. A receiver can then map them to its own data without access to the app's catalogue.
- **Sharing**: through the File System Access API where available (save in place), otherwise download/upload. The Web Share API is used on mobile (S).

## 9. Assumptions
- The track geometry needs to be accurate enough for planning (±0.5 mm), not for building track.
- End profile drawings are not in the Registry today. They are drawn in the app from the published PDF drawings of FREMO (all scales) and MMM (MMM-2R, MMM-3R), starting with FREMO H0, MMM-2R, MMM-3R and FREMO N.
- One module drawing corresponds to one physical module, which may consist of several sections. A module that can be set up in several ways is several modules.

## 10. Module Registry integration
The app never talks to the Registry as a user with rights. Access control is entirely the Registry's concern.

**Coming Registry release (Registry-side work, enabled by EX-7):**
- A user uploads a module file to a module in the Module Registry. The Registry validates it against the published module schema, stores it, and can show it (replacing or complementing the DWG/SKP document links).
- An end profile drawing is stored with the Registry's **EndProfile** entity (complementing its PDF document). End profile drawings are maintained there and **imported into the app**, so modules are drawn with the current profiles.
- **Properties are completed on upload:** the Registry fills in module properties that are missing in the uploaded file from its own data, such as the owners' names, the prefix, the number and the name (*FullName*), so that module files downloaded from the Registry afterwards have all properties set.
- **Package:** a module's package label (the box it is transported in) is saved in the module file and can be entered in the app. When a module file is uploaded, the Registry takes the file's label only if it has none itself; otherwise the Registry's label holds and is written into the file (decided 2026-11-19).
- **Data flows back:** when a module drawing is uploaded, the Registry can set missing properties and update measures from the drawing: exits, straight/radius/angle/length, width, sections, through tracks and flags (ModuleDrawing.md §8.8). The module file therefore includes the derived values. This improves the Registry data, where 71 % of the modules have no exits today.
- Meeting organisers can then get module files of registered modules from the Registry, or collect them in any other way.

**Reuse in the Registry (enabled by NF-10):**
- The Registry embeds the display components (EX-8) to show module and end profile drawings on its pages.
- The Registry **auto-draws** simple straight and curved modules from its own module data with the model library (MD-20) and stores the module JSON, so most modules get a drawing without anyone drawing them by hand.

**Later phase in this app (not in first release):**
- A read-only Registry API for scales, standards and end profiles, including end profile drawings (catalogue import, CA-5), and possibly for downloading module files the user has access to in the Registry.
- The Registry has no concept of standard add-ons today. Until it has, add-ons are a drawing-app concept; the module file carries them by short name.
- Import maps Registry *Module*, *ModuleExit*, *ModuleEndProfile*, *ModuleStandard* and *ModuleOwnership* to the drawing model and generates a template outline from length/radius/angle (MD-3).

**Variant mapping.** One drawing is one Registry *Module* row. The Registry stores the variants of a module, e.g. a station with or without a middle section, as separate *Module* rows with different *ConfigurationLabel*. Each of them is a separate module drawing, with its own file and id. Only the Registry knows that they belong together; the concept does not exist in this app, its files or the hall plan. The Registry keeps its module id in its entry of the module's external references (§6), as `moduleId` (a number), so that upload and import can map the drawing to its Registry row.

**Shared layout model.** A module in this app is the module of the NuGet package `Tellurian.Trains.Schedules.Model.Layouts`, with this app's own parts added: its name, prefix, number, configuration and package label, the names of its owners, its standard with the scale, its operation location (MD-24) and its tracks (MD-8) are that package's types and have its names in a module file. This app adds the module's GUID, the id of its standard in the catalogue, its other properties and the drawing. The designation is written with a space here (*SFjä 0012*), while the package's own `Designation` has none. The package is owned by the Schedules repository (`../Tellurian.Trains.Schedules`, project `Model.Layouts`, design in its `Documentation/OperationLocations.md`) and is used by the planner, the Module Registry, Module Draw (this app) and Dispatch. Lengths in the shared model are in metres.

## 11. Open questions
*None at the moment.*

### Resolved
- **Adjustable modules**: none are known, so loop closure is only reported. Adjustable modules are a later item (MD-16) (decided 2026-11-13).
- **Authoritative end profiles**: FREMO standardises FREMO end profiles in all scales and MMM standardises MMM-2R and MMM-3R, with the add-ons MMM-Summer and MMM-Modern to MMM-2R. Both publish PDF drawings, which are the sources for their end profiles in a catalogue (CA-1) (decided 2026-11-13).
- **Multi-section modules**: a module of one or more sections is **one drawing**. Internal end profiles are free; outer end profiles are of the module's scale (MD-4, MD-4a, MD-5) (decided 2026-11-13, refined 2026-11-16; alternate drawings, called variants, withdrawn 2026-11-19).
- **No variants**: a module drawing is one complete module, with one drawing. A module that can be set up in several ways is several modules, each with its own file and id; only the Module Registry knows that they belong together (MD-13 withdrawn, HP-7, §10) (decided 2026-11-19).
- **Track list and operation location**: every module has a list of its tracks, with at least one track. The operation location is optional; a module without it is plain line. Both are types of the shared layout model, `Tellurian.Trains.Schedules.Model.Layouts` (MD-8, MD-24, §10) (decided 2026-11-19).
- **Hall plan lines and exits**: a line is a list of modules, each turned or not; a module with three or more exits also says which exit the line continues from. A hall plan refers to an exit by its side and number, never by label; exit labels are free text for the reader (§3, §3.1, HP-4) (decided 2026-11-19).
- **End profiles per exit**: each exit has its own end profile and orientation (as drawn or mirrored, since the end plate can be fitted either side out). The exits of a module may use end profiles of different standards of the same scale, e.g. FREMO and MMM. Auto-draw mirrors an asymmetric profile at the far end so that its asymmetric feature stays on one side of the track; an *Endewender* (Registry flag *IsEndProfileSwitcher*) turns it over instead (MD-5, MD-20, ModuleDrawing.md §4.3) (decided 2026-11-16).
- **Operator space and public side**: modules can have operator spaces on one or both sides, and marked public sides. Overlapping operator spaces are a warning that the planner can acknowledge. The acknowledgement is invalidated when an involved module changes and the overlap still exists (MD-17, MD-18, HP-15, VA-11). Operator spaces and public sides belong to the module drawing; modules are read-only in a hall plan (HP-16) (decided 2026-11-13).
- **Public areas, walking paths and duck-under**: the hall plan has public areas and walking paths for train drivers. The duck-under area is part of the module drawing, and walking paths may only cross modules under duck-under areas (MD-19, HP-17, HP-18, VA-13) (decided 2026-11-13).
- **Standard add-ons**: a standard can have add-ons (e.g. MMM-Summer and MMM-Modern on MMM-2R). Modules state which add-ons they meet, and hall plans can prefer add-ons; modules not meeting them get a warning (VA-14) (decided 2026-11-13).
- **Reuse in the Module Registry**: all view components are in a separate component library (NuGet), usable in Blazor Server; simple modules can be auto-drawn from Registry data, producing module JSON for storage in the Registry (MD-20, EX-8, NF-10) (decided 2026-11-13).
- **Module identification**: a module has a FREMO number with the owner's prefix, a name, or both; the owner's full name is optional and filled in by the Registry on upload (decided 2026-11-16). Since 2026-11-19 the prefix and the number are properties of the module, and the owners are one text with their names.
- **The module of the shared layout model**: a module is the shared contract's module with this app's parts added, and enum values in files are written as in the code, as the contract does. All five file kinds are at schema version 2 (decided 2026-11-19).
- **Hosting**: Azure Static Web Apps (decided 2026-11-13).
- **Target framework**: .NET 11 (decided 2026-11-13).
- **End profiles are drawn in the app** (2D end view) and compared geometrically (decided 2026-11-13).
- **Heights are offsets**: rail-top offset 0 = the standard's height (normally 1300 mm above floor). Rare ramp modules have exits with non-zero offsets; hall plans check heights at joints (MD-7a, HP-13, VA-10) (decided 2026-11-13).
- **Vertical datum** is the top of rail, RÖK (typically 1300 mm above the floor). Plate height is not a fit criterion; screw-hole positions decide whether ends are bolted, clamped or incompatible (decided 2026-11-13).
